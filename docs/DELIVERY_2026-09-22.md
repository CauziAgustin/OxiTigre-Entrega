# Entrega técnica OxiTigre — 22 de septiembre de 2026

## Resumen ejecutivo

Esta entrega presenta una versión funcional local del sistema OxiTigre para Windows, respaldada por una API central y
SQL Server. El corte incluye aplicación de escritorio, API, panel administrativo web, base de datos, instaladores,
documentación y pruebas automatizadas. La aplicación móvil permanece en desarrollo y se excluye expresamente de esta
entrega.

El sistema aplica trazabilidad de las operaciones: los cambios relevantes conservan usuario, fecha, estado, documento,
correlación y movimientos compensatorios cuando corresponde. Las bajas funcionales son lógicas y las operaciones
confirmadas no se reescriben para ocultar su historia.

## Arquitectura

```text
WinForms ───────────┐
Admin Web ──────────┼── HTTP/HTTPS ── API ASP.NET Core
                    │                       │
                    │                  reglas BLL
                    │                       │
                    └────────────────── contratos compartidos
                                            │
                                         DAL SQL
                                            │
                                  Stored Procedures versionados
                                            │
                                         SQL Server
```

La solución es un monolito modular con arquitectura por capas:

- **Presentación:** WinForms y panel Blazor. No acceden directamente a SQL Server.
- **API:** frontera HTTP, autenticación, autorización y validación de solicitudes.
- **BLL:** reglas de negocio y transiciones permitidas, independiente de la interfaz.
- **DAL:** acceso parametrizado mediante `Microsoft.Data.SqlClient` y Stored Procedures.
- **Domain y Contracts:** modelos internos y contratos estables compartidos.
- **SQL Server:** integridad, transacciones, numeración, saldos e historial durable.

Las dependencias avanzan hacia el dominio y no desde la base hacia la interfaz. Esta separación permite cambiar una
pantalla sin duplicar reglas, probar el negocio sin abrir WinForms y reutilizar la API desde otros clientes.

La interfaz incluye español e inglés y permite importar un paquete JSON de otra cultura. Antes de instalarlo valida
esquema, cultura canónica, claves conocidas, textos, tamaño y placeholders; las claves no incluidas usan español como
respaldo. El idioma se mantiene separado de las reglas y datos del negocio. La guía y un JSON portugués de ejemplo
se incluyen en `docs/INTERNATIONALIZATION.md` y `docs/examples/IDIOMA_PORTUGUES_EJEMPLO.json`.

## Buenas prácticas aplicadas

- **Separación de responsabilidades:** UI, API, negocio, datos, dominio y contratos son proyectos distintos.
- **API como única entrada:** los clientes no conocen credenciales ni estructura interna de SQL Server.
- **Seguridad por defecto:** contraseñas con hash, sesiones opacas, expiración, revocación, bloqueo y permisos por rol.
- **Validación en fronteras:** se validan contratos HTTP, reglas de negocio y constraints de base de datos.
- **SQL parametrizado:** la DAL no concatena entradas del usuario en consultas.
- **Transacciones e idempotencia:** confirmaciones y movimientos relacionados se ejecutan de forma atómica.
- **Trazabilidad inmutable:** las correcciones relevantes generan compensaciones y conservan la operación original.
- **Baja lógica:** proveedores, clientes y catálogos se desactivan sin destruir referencias históricas.
- **Concurrencia optimista:** `rowversion` evita sobrescribir cambios simultáneos silenciosamente.
- **Migraciones versionadas:** los cambios SQL tienen orden, historial y registro SHA-256.
- **Secretos fuera del código:** conexiones y valores sensibles se reciben por variables o User Secrets.
- **Calidad automática:** nullable habilitado, warnings tratados como errores, builds determinísticos y tests repetibles.
- **Accesibilidad operativa:** formatos argentinos, filtros parciales, ayudas contextuales y mensajes orientados a la acción.
- **YAGNI:** se usan capacidades nativas y dependencias existentes; las integraciones externas se agregan cuando existe
  proveedor y requisito confirmado.

## Documentación del código

El repositorio aplica una política verificable y útil para mantenimiento:

- cada archivo C# y SQL posee encabezado de proyecto, componente, versión, fecha, finalidad e historial;
- todos los métodos declarados en C# —públicos, internos y privados— poseen documentación XML y el compilador genera
  el archivo de documentación;
- se utiliza `<summary>` para el propósito, `<param>` para cada argumento, `<returns>` cuando existe retorno y
  `<exception>` únicamente cuando el contrato puede producir esa excepción;
- los flujos internos de ventas, logística, compras, finanzas, seguridad y configuración tienen XML descriptivo;
- los 80 Stored Procedures explican tipo, entradas, salidas, retorno, tablas, transacción y auditoría; los Commands
  consolidados también detallan cada valor permitido de `@I_ACCION` y su permiso;
- SQL y C# mantienen indentación, bloques separados y formato uniforme mediante `.editorconfig`;
- `Test-DocumentationStandards.ps1` y `Test-CSharpDocumentation.ps1` controlan estas convenciones; el segundo exige
  resumen, parámetros y retornos aplicables en todos los métodos y rechaza descripciones genéricas conocidas.

Esta política evita tanto la falta de contexto como los comentarios redundantes que envejecen separados del código.
Los comentarios y contratos documentales no generan por sí solos una nueva versión ni una entrada de historial.

## Compilar y validar el alcance entregado

Desde la raíz del repositorio:

```powershell
./scripts/ci/Test-DesktopDelivery.ps1
```

Ese comando restaura, compila en `Release`, ejecuta las pruebas .NET y valida repositorio, documentación, SQL, filtros
de fecha y reglas de los dashboards. Usa `OxiTigre.Desktop.slnf`, que excluye Mobile de forma explícita.

La integración real API-SQL se comprueba por separado porque requiere SQL Server Testing instalado:

```powershell
./scripts/ci/Test-ApiSqlIntegration.ps1
```

## Ejecutar la demostración

Con SQL Server local ya instalado, abrir dos PowerShell en la raíz.

API:

```powershell
./scripts/development/Start-Api.ps1
```

Escritorio:

```powershell
./scripts/development/Start-Desktop.ps1
```

Recorrido recomendado para exponer:

1. iniciar sesión y seleccionar empresa/sucursal;
2. mostrar Inicio y sus prioridades operativas;
3. recorrer Comercial e Inventario;
4. abrir Compras y explicar una recepción parcial;
5. mostrar Trazabilidad: tubo, contenido, incidente, fraccionamiento e historial;
6. abrir Logística y explicar prioridades, ventanas y paradas;
7. mostrar Finanzas aclarando que el recibo es interno y no fiscal;
8. cerrar sesión y explicar revocación y auditoría.

## Generar el artefacto

La versión oficial debe generarse desde un árbol Git limpio y versionado:

```powershell
./scripts/ci/Build-Release.ps1 -Version '2026.09.22'
```

El ZIP contiene API, WinForms, Admin Web, scripts de base, documentación operativa y `manifest.json`. El manifiesto
declara el commit, el alcance `DesktopApiDatabase`, la exclusión de Mobile y el SHA-256 de cada archivo. El parámetro
`-AllowDirty` existe solo para candidatos locales y deja esa condición registrada; no debe usarse para la entrega final.
